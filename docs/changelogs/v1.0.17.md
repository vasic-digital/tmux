## A41 — Double session-name prompt on bash-login terminals (Bug)

**Symptom.** On a new terminal the operator is asked for a session name;
pressing Enter for no session prompts AGAIN — twice in a row.

**Root cause (reproduced on the affected host, no guessing per §11.4.6).**
On Linux/bash a single login-shell PROCESS sources `tmx-shell-init.sh`
TWICE: `.bash_profile` carries the source line AND sources `.bashrc`, which
also carries it. The blank/`default` branch RETURNS (it does not `exec`), so
`.bash_profile` then continues, sources `.bashrc`, and the second source
re-prompts. The name-entry branch `exec`s and replaces the process before
`.bashrc` is reached — which is exactly why the operator only saw it on the
press-Enter / no-session path. Measured: nezha `bash -l -i` → PROMPT_COUNT=2;
macOS zsh `-l -i` → 1 (zsh sources `.zshrc` once per process, so Mistborn
never showed it).

**Fix (§11.4.1 — at source, not at the rc call sites).** A per-process,
NON-exported idempotency guard `_TMX_SHELL_INIT_PROMPTED` was added to
`scripts/tmx-shell-init.sh.template` immediately before the prompt. It makes
the interactive prompt fire at most once per shell process while resetting
for each new shell process, so every new terminal still prompts exactly once.
The legitimate single-source first prompt is preserved (verified).

**Captured evidence (4-layer).**
- L1 parseability: `sh -n` clean (§11.4.67).
- L3 runtime: `scripts/tests/54_double_prompt_idempotent.sh` — PTY harness
  reproducing the `.bash_profile`→`.bashrc` double-source in one process —
  RED `prompt_count=2` → GREEN `prompt_count=1`, 3/3 deterministic (§11.4.50).
- L4 paired mutation: `M-DBLPROMPT` strips the guard and asserts test 54
  FAILs — CAUGHT.
- On-affected-host (§11.4.39): nezha real-HOME `bash -l -i` PROMPT_COUNT
  2 → 1 after deploy.

## A42 — Mouse select/copy unusable in tmx panes, especially Claude Code (Bug)

**Symptom.** Cannot select/copy with the mouse in any tmx/tmux window,
especially inside the `claude` TUI.

**Root cause (evidence-based).** NOT a stale config — the live server already
had `mouse on`, the `M-/S-MouseDrag1Pane → copy-mode -M` overrides, and a
working `@clip`→`pbcopy` pipe (verified via round-trip + in-tmux keyboard
copy). The defect was discoverability + a cross-terminal trap: inside a
mouse-tracking app (`#{mouse_any_flag}`, e.g. Claude Code) a PLAIN drag is
forwarded to the app by design (so the app keeps its own mouse), and on
iTerm2 with the default *Option Key Sends = Normal* (confirmed via
`defaults read com.googlecode.iterm2`) Option/Alt-drag is consumed by
iTerm2's OWN native-selection bypass and never reaches tmux's
`M-MouseDrag1Pane`. That left only Shift-drag reaching tmux — undiscoverable.

**Fix.** Added a terminal-agnostic mouse-toggle to
`scripts/tmux.conf.template`:

```tmux
bind m set -g mouse \; display-message 'mouse #{?mouse,ON …,OFF (use native terminal selection: drag + Cmd-C)}'
```

`prefix m` toggles tmux mouse OFF, so the outer terminal's NATIVE selection
(drag → Cmd-C / right-click → Copy) works EVERYWHERE — including inside Claude
Code; `prefix m` again restores tmux scrollback + copy-mode. The reliable
gestures (Shift-drag for in-tmux selection; `prefix m` for native selection)
are documented in the config and `docs/guides/clipboard.md`.

**Captured evidence (4-layer).**
- L1 config-load: `scripts/tests/55_mouse_toggle_and_copy.sh` asserts the
  `prefix m` binding loads.
- L3 runtime: test 55 PASS, 3/3 deterministic — toggle flips `mouse on→off`,
  Shift-drag override present, copy-pipe delivers the selection to an external
  sink.
- L4 paired mutation: `M-MOUSETOGGLE` strips the binding and asserts test 55
  FAILs — CAUGHT.
- Real-mouse layer: `scripts/tests/56_real_mouse_drag_copy.sh` drives a genuine
  Shift-drag via `cliclick` over a real iTerm2 window when available; honest
  §11.4.3 SKIP where the GUI-automation topology (cliclick / Accessibility) is
  absent.
